
## SSL握手协议——阶段3

阶段3：客户端认证和密钥交换

+ > certificate消息（可选）
+ - X.509 v3证书链
+ > client_key_exchange消息
+ - 发送客户端密钥交换信息
+ - RSA密钥交换
+ - 客户端生成48字节的预主密钥（预主密钥），并使用服务器证书中的公钥或服务器密钥交换消息中的临时RSA密钥加密
+ - 匿名DH或瞬时DH
+ - 发送客户端的DH公钥参数
+ - 固定DH
+ - 由于certificate消息中包括了DH公钥参数信息，因此，此消息内容为空
+ > certificate_verify消息（可选）
+ - 通过对基于前述消息散列码的签名，对客户端证书的认证。

```
CertificateVerify.signature.md5_hash =
MD5(master_secret || pad_2 || MD5(handshake_messages || master_secret || pad_1))
Certificate.signature.sha_hash =
SHA(master_secret || pad_2 || SHA(handshake_messages || master_secret || pad_1))
```

## SSL握手协议——阶段4

+ 阶段4：完成
+ > change_cipher_spec消息
+ - 向当前的CipherSpec中拷贝挂起的CipherSpec
+ > finished消息
+ - 使用新算法、密钥对密钥交换过程和认证过程中的正确性进行验证
+ MD5(master_secret || pad2 || MD5(handshake_messages || Sender || master_secret || pad1))
+ SHA(master_secret || pad2 || SHA(handshake_messages || Sender || master_secret || pad1))
+ > 服务器与客户端消息类似

## SSL握手协议——密码计算

+ - 主密钥创建
+ - 交换次密钥（预主密钥-pre_master_secret）
+ - RSA
+ - 由客户端生成48字节（384位）的次密钥，用服务器RSA公钥加密后发往服务器
+ - DH
+ - 客户端和服务器同时生成DH公钥，交换并计算次密钥
+ - 计算主密钥（master_secret）

```
master_secret =
    MD5(pre_master_secret || SHA('A' ||
        pre_master_secret ||ClientHello.random ||
        ServerHello.random)) ||
    MD5(pre_master_secret || SHA('BB' ||
        pre_master_secret || ClientHello.random ||
        ServerHello.random)) ||
    MD5(pre_master_secret || SHA('CCC' ||
        pre_master_secret || ClientHello.random ||
        ServerHello.random))
```

## SSL握手协议——密码计算

+ 生成密钥参数
+ > 生成CipherSpecs中的客户端写MAC密钥、服务器写MAC密钥、客户端写密钥、服务器写密钥、客户端写初始矢量、服务器写初始矢量
+ > 生成方法

```
key_block =
    MD5(master_secret || SHA('A' ||
            master_secret || ServerHello.random ||
            ClientHello.random)) ||
    MD5(master_secret || SHA('BB' ||
            master_secret || ServerHello.random ||
            ClientHello.random)) ||
    MD5(master_secret || SHA('CCC' ||
            master_secret || ServerHello.random ||
            ClientHello.random)) || ...
```

+ - 一种开放的加密安全规范

+ - 参与开发的公司有（1996年）
+ - MasterCard, Visa
+ - IBM, Microsoft, Netscape, RSA, Terisa和 Verisign
+ - 不是一个支付系统，而是安全协议和格式集合

+ - SET提供三种服务
+ - 为交易各方提供了安全信道
+ - 通过使用X.509v3数字证书提供信任
+ - 由于信息只在需要的地方和时间提供，因此确保了私密性

## 安全电子交易（SET）

+ SET主要特征

+ 信息保密性
+ • 持卡人账号和支付信息在网络传输过程中是安全的，提供了一种防止（商家）获取持卡人信用卡号码的机制

+ 数据完整性
+ • 使用数字签名，保证订购信息、支付信息、个人数据的完整性

+ 持卡人账号认证
+ • 商家能够验证持卡人是否为合法卡账号的合法用户（使用x.509v3证书）

+ 商家认证
+ • 持卡人能够验证商家是否与允许接收支付卡的金融机构建立联系（使用x.509v3证书）

## SET——交易过程

+ 1. 客户开通账号。如MasterCard或Visa
+ 2. 客户接收签发的x.509v3证书
+ 3. 商家拥有他们自己的证书
+ - 两种公钥证书，一个用于签名消息，一个用于密钥交换
+ 4. 客户进行订购
+ - 客户发购买清单，商家返回订购单（商品、单价、总金额、订单号）
+ 5. 商家被验证
+ - 客户通过商家的证书，验证正在与一个合法的商家进行交易
+ 6. 发送订购和支付信息
+ - 支付信息包括信用卡细节，通过加密使商家无法获得这些信息
+ 7. 商家请求付款认证
+ - 商家将付款信息发给支付网关，请认证客户提供的信用卡可以支付此次购买
+ 8. 商家确认订购
+ - 商家向客户发送订购确认消息
+ 9. 商家提供商品或服务
+ 10. 商家请求付款

## SET——双重签名

+ - 客户创建2个信息
+ - 订单信息（OI）给商家
+ - 支付信息（PI）给银行
+ - 需求
+ - 商家和银行不需要知道全部2个信息
+ - 但需要知道2个信息是绑定的
+ - 解决方案：双重签名
+ - DS = E_KRC [ H( H(PI) || H(OI) ) ]

![](img/0935d481fd26d10140d7cd560b6540ba_590_0.png)

PI = Payment Information
OI = Order Information
H = Hash function (SHA-1)
|| = Concatenation
PIMD = PI message digest
OIMD = OI message digest
POMD = Payment Order message digest
E = Encryption (RSA)
KRc = Customer's private signature key
