## Windows 高级题

客户端类`UPX`壳，没法用`UPX`自动脱壳，因此用“`ESP`定律”脱，脱下来随便修复下（不用能跑，`ida`里能看即可）。

服务端 Themida 强壳，但[//github.com/ergrelet/unlicense](https://github.com/ergrelet/unlicense)非常nb，按提示在`conda`里装个`python` 3.10 32-bit：

```
conda create -n py310_32
conda activate py310_32
conda config --env --set subdir win-32
conda install python=3.10
conda activate py310_32
```

然后用这个工具就可以完美脱壳，并能正确运行。

然后有一些反调试，但是`x64dbg`下用 ScyllaHide Themida Profile 基本都能自动过掉，无须操心。

`ida`里阅读客户端代码可知调用的是 out-of-process 的、 .exe 的 COM 接口。服务端注册后，客户端获得 COM 对象时 Windows 就会自动启动服务端，随后通过RPC受理调用请求。

在 Windows SDK 里找到`oleview`工具（我的电脑上在`C:\Program Files (x86)\Windows Kits\10\bin\10.0.22621.0\x86\oleview.exe`），File 菜单下选 View Typelib，选择服务端程序，可以得到 RPC 接口的 IDL：

然后就是想个办法定位到服务端这些函数的位置，我找了半天找不到（事后反过来找发现可以从`ATL::CComObject`或`ATL::CComContainedObject`的`vftable`入手（根据网上的[//github.com/smourier/OutOfProcessCOMServer/blob/main/OutOfProcessCOMServer/Mouse.h](https://github.com/smourier/OutOfProcessCOMServer/blob/main/OutOfProcessCOMServer/Mouse.h)可知，实际用户编写的类是个抽象类，其`vtable`并不实际生成（`ATL_NO_VTABLE`），需要找到它的子类才有这些虚函数指针））。

注意到客户端有一些共享内存的逻辑，猜测服务端也有，因此从相关函数的导入表开始查询交叉引用定位到了`ATL::CComObject`的构造函数。
