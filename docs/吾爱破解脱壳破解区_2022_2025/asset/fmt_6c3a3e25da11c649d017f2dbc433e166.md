## 初步想法

这个程序以前因需要满足特定的需求，我曾反编译修改过它依赖的 C# 的 `dll` 库文件。这个 `exe` 运行时要安装 `net461`，所以这个程序大概还是 .NET 的。需求是要在界面上显示名字，若通过修改 `dll`，在前面绿色字“月卡车不在有效期内，入场”，在这里附加字串的话，会容易实现一些，但可能会影响其它数据的正确性。所以直接修改 `EXE` 文件才是正确的方法。

## 第二步：摸石头

确定为 .NET 框架的程序。但不确定有没有壳，似乎有壳，先不管。将它放在 `ILSpy9`、`dnspy618`、`.NET Reflector11` 看代码及函数都没有混淆痕迹，且 `ILSpy9` 和 `.NET Reflector11` 还能看到有 `xaml` 文件，且都没有乱码和随机函数名。于是直接导出工程文件到 `VS2019`。

`ILSpy9` 导出过 C# 的 SDK 及非 SDK 版本的多个不同版本，`dnspy618` 导出过 C# 和 VB，这个不能选版本，`.NET Reflector11` 导出过 C# 和 VB 的多个版本。这三个导出的工程的格式各不相同，但有一个共同点就是，都非常多的错误。每个都尝试修复错误后，感觉还有无穷无尽错误提示，都不得不放弃修正了。

几天时间在这三个工具导出的工程文件之间不断的尝试修复错误，期间也尝试过 `dotpeek`，似乎还更差劲了。最终的结论是：

问了 AI，指出的方法都不起作用。而且不能解包资源文件 `ParkingManage.g.resources`，尝试多次后，无奈放弃。

`dnspy618` 导出的工程可以列出几千个错误，替换完 `<>` 变量，修复引用后，还是一大堆，最后发现还不解包资源文件 `ParkingManage.g.resources`，最终也放弃了。

因为 `Die` 检测为 VB 编写，且引用里也有 VB 的库，本来偏向于 `.NET Reflector11` 和 `dnspy618` 导出的 VB 工程。最后不得不都放弃了，不想一个一个的将 `xaml` 文件放到工程中去，太多了。

因 `win7` 只支持到 `vs2019`，还尝试安装了一个 `win10` 系统，再装了了一个 `VS2022`，效果也还是一样的。于是还是切回到 `win7` 里面。

`ILSpy9` 似乎成了唯一的绝唱了，尽管错误多，但是记得有个版本已经修复得差不多了。

上面几个工具导出的工程，在 `vs` 中有的不能添加引用，有的不能更改为 `.net461`，只有 `.net4.0`，有的感觉完全就是不能识别到类，也改不了，一大堆问题，头大。

慢慢的分析出主要的问题集中在 WPF 的 `Xaml` 上，因为本人确实不是做软件开发的，只是对写程序有独特兴趣，都还不了解 WPF 和 `winform` 的根本区别，网上搜索关于 WPF 的反编译，结果很少有提及这方面的记载。自己在 `VS2019` 中新建一个简单的 WPF 的 VB 工程后，生成的 `exe` 直接导入到 `Ilspy` 再导出代码到 `VS`，来找规律，发现也是错误很多，还不如直接反编译原版，有错改错，少走冤枉路。

## 第三步：过河

从 `ILSpy9` 导出的 C# 工程中挑了印象中一个稍好的 C# 6 的版本，再手动修改 `csproj` 的 C# 版本到 7.3，后面经不不断的摸索，终于是把错误都修复完了。于是说明了 `Ilspy` 这条路是通的。现在来复现一下处理过程，记录经验。

因为 `.net4.6.1` 默认支持的 C# 6.0，`win7` 下 `vs2019` 基于 `.net4.6.1` 的 C# 版本最好是到 7.3。所以从 `ILSpy` 以 C# 6.0 的版本导出 `park` 原版的工程，理论上直接导出 C# 7.3 也是可以的。
