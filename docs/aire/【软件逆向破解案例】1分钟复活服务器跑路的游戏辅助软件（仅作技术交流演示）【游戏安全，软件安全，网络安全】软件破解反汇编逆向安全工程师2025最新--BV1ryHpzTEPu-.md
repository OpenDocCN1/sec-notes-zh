## 软件逆向破解案例教程：02：客户端依赖服务器的基本原理 🔌

上一节我们介绍了原文含义与合规边界，本节我们来看看客户端和服务器之间的基本关系。大白话讲，很多软件启动时会先问服务器“我能不能用”，服务器回答“能”或“不能”，客户端再决定是否打开功能。服务器跑路以后，客户端问不到答案，就可能一直转圈、报错或者直接退出。理解这个流程，比一上来就改程序更重要。


核心判断可以用一个简单公式表示，运行条件不是单一开关，而是多个条件同时满足。

```text
客户端可运行 = 本地校验通过 AND 服务器校验通过 AND 功能开关打开
```

正常流程可以用下面的伪代码描述，这里只表达概念，不涉及具体破解操作。

```c
if (license_ok && server_ok) {
    enable_feature();
} else {
    show_error();
}
```

以下是客户端启动时常见的概念流程，帮助初学者建立整体印象。

- 第一步，客户端读取本地配置，比如版本号、账号状态和缓存信息。

- 第二步，客户端向授权服务器发送请求，请求里可能包含账号、设备信息和版本号。

- 第三步，服务器返回结果，客户端解析返回字段，判断是否允许进入功能。

- 第四步，如果服务器不可达，客户端可能显示错误、进入离线模式，或者直接停止运行。

- 第五步，分析者要做的不是马上修改，而是先记录现象，确认问题到底出在网络、配置还是本地判断。

通过这一节可以看到，“服务器跑路”并不等于客户端一定坏了，而是客户端依赖的外部条件消失了。下一节我们来看看在授权范围内，怎样从黑盒观察到可验证的分析流程。

## 软件逆向破解案例教程：03：从黑盒观察到可验证分析 🛠️

上一节我们介绍了客户端依赖服务器的基本原理，本节我们来看看分析流程怎样一步步推进。对初学者来说，最直白的做法是先观察、再记录、后验证，不要一上来就盯着反汇编代码。因为程序是一个整体，网络请求、配置文件、启动日志和界面提示都可能提供线索。分析的目标是理解行为，而不是对他人软件做未授权修改。

以下是授权环境下的分析步骤，每一步都强调记录证据和保持合规。


- 先准备隔离环境，例如虚拟机、测试账号和日志目录，避免影响真实工作环境。

- 再观察启动现象，记录报错文字、界面状态和等待时间，判断程序是卡在网络请求还是本地校验。

- 然后查看网络请求的去向，记录请求地址、参数类别和返回字段的含义，但不要对真实服务器做干扰。

- 接着做静态观察，用反汇编器或调试器理解程序结构，只做阅读和标注，不修改他人程序。

- 最后做本地验证，如果软件属于自己或已获得授权，可以搭建测试服务模拟返回结果，验证客户端逻辑。

核心概念可以用“判断点”来描述，程序最终会走到一个条件分支，条件成立就进入功能，不成立就显示错误。

```c
if (check_result == true) {
    enter_feature();
} else {
    show_message();
}
```


需要再次强调，这里讲的是“理解判断点”的方法，不是提供补丁地址或绕过步骤。对于服务器跑路的第三方软件，合规做法包括联系作者、使用官方离线版本、寻找替代工具，或者只对自己拥有源码和授权的软件做修复。到这里，我们已经把分析流程讲完了，下一节我们来看看测试和记录怎么做。

## 软件逆向破解案例教程：04：授权测试与过程记录 ✅

上一节我们介绍了从黑盒观察到可验证分析的流程，本节我们来看看测试和记录。初学者容易只看结果，不看过程，最后出了问题也说不清楚。大白话讲，测试就是“在可控环境里试一下”，记录就是“把每一步写下来”，这样既能复盘，也能证明自己是在授权范围内学习。对于游戏辅助软件，还要额外注意它可能违反游戏规则，不能把技术学习变成作弊工具。

以下是测试与记录时建议保留的内容，方便后续复盘和写报告。

- 记录环境信息，包括操作系统、软件版本、测试时间和是否使用虚拟机。

- 记录现象信息，包括启动报错、界面截图、日志片段和网络请求概况。

![](img/f28c55a3bfe6173849535d0eb23d5f92_8.png)

- 记录分析信息，包括观察到的判断逻辑、依赖服务和不确定点。

- 记录合规信息，包括软件来源、授权说明和“仅作技术交流演示”的范围。

- 记录结论信息，包括问题是服务器不可达、配置缺失还是本地判断失败。

> 本教程仅用于技术交流和学习演示。请勿对他人软件进行未授权修改、绕过授权或传播破解工具；游戏辅助软件本身也可能违反游戏规则和相关法律法规。
